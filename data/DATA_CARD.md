# ShopEasy Synthetic Data Card (Annex E)

**Pinned evaluation date (as_of_date):** 2026-10-06. All edge-case expected values are
computed against this date, matching the case study's Annex A.3 worked example.

## Purpose
Synthetic customer, product, order and return data for the AI-Powered Retail Customer
Support Agent. It exercises: personal-tool questions (eligibility, refunds, order status,
warranty), version/conflict resolution (rule registry + circulars), safety (injection note,
other-customer refusals), and honest abstention. The retailer "ShopEasy" is fictional;
the data contains no real persons.

## Generation method
- **Model:** Generated using Claude 3.5 Sonnet and Qwen 2.5 7B with JSON schema enforcement, combined with a **deterministic, seeded Python script** (`scripts/generate_data.py`, `random.seed(20261006)`).
- **Verbatim Prompts:** Stored verbatim in `data/prompts/`:
  - `data/prompts/customers_prompt.txt`: Customer generation prompt enforcing Annex C constraints and tier distribution.
  - `data/prompts/products_prompt.txt`: Product catalog generation prompt across 5 categories with warranty constraints.
  - `data/prompts/orders_prompt.txt`: Background order and order item prompt enforcing referential integrity.
- **Hand-authored Edge Cases:** The 16 edge orders (O-100001–O-100016) and the 13 rule registry entries were authored to exact frozen values by hand inside the script; background rows (50 orders, names, cities) are programmatic and seeded.

## Schema and validation
`scripts/validate_data.py` enforces (52 checks, 0 violations — see `validation_report.txt`):
- Exact Annex C columns; ID formats (C####, O-######, R-######); enum values
- No reserved judge identifiers (C9000–C9999, SKU-JDG*, O-900000+)
- Foreign keys across all tables; every return refers to an existing order item
- `delivered_on` only when the order is DELIVERED and never before `order_date`
- `net_unit_price ≤ list price`, `qty ≥ 1`, `price > 0`, `warranty_months ≥ 0`
- Distribution minimums (below) and presence of every deliberate edge case with its
  frozen expected value (refund math re-computed with Decimal: 2639.10, 3539.10, 80931.00, 2939.00)

## Distribution
- **Customers:** 32 — STANDARD 23, GOLD 5, PLATINUM 4
- **Products:** 27 — ELECTRONICS 10, FASHION 5, HOME 4, BEAUTY 4, GROCERY 4
- **Orders:** 66 — 16 edge (O-100001–O-100016) + 50 background (O-200001–O-200050);
  statuses approx. DELIVERED 43, SHIPPED 13, PLACED 6, CANCELLED 5
- **Order items:** 78 rows; **Returns:** 3 (REQUESTED, REFUNDED, PICKED_UP)
- **Rules:** 13 across 5 source documents; **Source register:** 8 documents (Annex B fields)

## Known gaps and biases
- All orders belong to a single fictional retailer; prices are round rupees.
- Background orders cluster between 2026-07 and 2026-10-06 (around the pinned as_of date).
- Payment methods and statuses are uniformly cycled, not weighted by real-world behaviour.
- Only 3 returns exist (the lifecycle tool's rejection paths are tested via eligibility, not volume).
- No multi-item edge orders beyond one SKU per edge order (ambiguity uses two orders instead).

## Privacy statement
All names, cities, orders and notes are synthetic; generated by the team's script. No real
customer, employee or retailer data was used anywhere in this kit.
