2. The problem
A retailer’s customers ask the same kinds of questions all day: can I return this, how much will I get back, is it under warranty, where is my order. The answers live in return and refund policies, warranty terms, shipping rules, promotional circulars and help-centre pages, and in each customer’s own order history. Rules change through new circulars, differ by product category and customer tier, and the help-centre text is often out of date.
Support agents answer inconsistently, and customers wait. Questions about a customer’s own situation (“Can I return my headphones?”) need the customer’s order records as well as the rules, and getting them wrong costs real money: a wrong refund, a wrongly refused return, or another customer’s data shown to the wrong person.
Your mission
Build an AI assistant that answers and acts on customer support questions using authorised retailer documents and authorised customer data and tools.
Its responses must be accurate, grounded and explainable, it must never fabricate information, and it must never reveal or act on another customer’s data.

3. Functional requirements
These requirements describe behaviour, not architecture. How you meet them (a single agent, specialist agents, a supervisor, or a fixed workflow) is your design decision, and you will be asked to justify it.
R1 Knowledge retrieval
Answer questions using the documents you ingest. Answers must come from retrieved text, not from the model’s general knowledge.
R2 Citations on every factual answer
Each factual answer must state the source document, section or page, version and effective date. Judges will open the cited page and check that it actually supports the answer.
R3 No fabrication
When evidence is insufficient, return answer_type: not_found with the message “I could not find this information in the authorised sources.” When evidence is partial, say clearly what is known and what is not.
R4 Versions and conflicts
Resolve conflicting or versioned documents using the Source Precedence Policy in Annex A: scope, supersession, authority and effective date, relative to the request’s as_of_date. Explain which rule applies and why. Documents that are not yet effective must not be treated as current; mention them as upcoming changes where relevant. If a conflict cannot be resolved by the policy, report it rather than silently choosing.
R5 Deterministic tools for authoritative results
Order lookups, eligibility decisions, refund calculations and warranty checks must be done by code (tools) over the SQLite data and the rule registry, never by LLM arithmetic or LLM judgement. The LLM selects tools and explains their results. Every threshold a tool uses (return window, fee, approval limit) must trace back to a cited document clause (rule registry, Annex C). Any tool that changes state (for example raising a return) must check eligibility itself and be safe to call twice.
R6 Multi-step requests
Handle questions that need several sources, tools and steps, including what-if questions (“what if I return it after 9 days?”, “what if I were a Gold member?”). State the assumptions you make.
R7 Authorisation and privacy
The customer’s identity comes only from the request context (the X-Customer-Id header), never from the message text. Refuse any request for another customer’s data, and do not let the response reveal whether another customer’s order exists. Do not log personal data you do not need.
R8 Untrusted content
Treat document content, order notes, reviews and customer messages as data, not instructions. Text inside any of them must never change the assistant’s behaviour, and must never be able to trigger a tool, a refund or a policy statement.
R9 Answer typing
Clearly distinguish a retrieved fact, a calculated result and an AI-generated explanation, using the answer_type field and the response structure in Section 6.
R10 Auditability
Every response has a trace_id and an audit record listing the sources retrieved, tools invoked (with inputs and outputs), rules applied, conflicts detected, model used, latency and tokens. Do not expose chain-of-thought; an audit summary is enough.
R11 Live ingestion
A new document and its metadata can be ingested through POST /ingest while the system is running, and is used immediately with no code change or restart. Judges will do this during judging with documents you have not seen, including a circular that changes a rule your tools use.
R12 Evaluation
Build an evaluation set and report measured results (Section 7). A system with no evaluation is incomplete.
4. Your data
4.1 Retailer documents: bring your own
Use official, publicly available policy documents. You may pick a real retailer whose return, refund, warranty and shipping policies are published on its website, or invent a fictional retailer and write its documents yourselves. You know which retailers your classmates use, so choose documents that make the problem genuinely interesting. Typical documents: terms of sale, return and refund policy, exchange rules, warranty policy, shipping and delivery terms, promotional or festive-season circulars, help-centre FAQs.
Minimum: 3 documents. More complex corpora earn more marks under the Document Complexity criterion. Complexity means:
Multiple versions, amendments or circulars that genuinely conflict with earlier rules (for example a circular that shortens a return window)
Rules that differ by category or customer tier (for example electronics versus fashion, or fees waived for premium members)
Tables (fee tables, window-by-category tables) and cross-references and exceptions (“subject to clause 4.1”)
Scanned or image-based pages that need OCR
Documents from different issuing authorities (legal terms, head-office circulars, help-centre FAQs)

Rules for documents
Only public, official documents, used in line with the website’s terms of use. Do not use any document containing real personal data.
Record every document in the Source Register (Annex B), including where you got it.
You may add up to 3 synthetic documents (for example, a mock circular or an unofficial forum post) to demonstrate conflict handling and untrusted content. Mark them synthetic: Y in the register.
4.2 Synthetic customer and order data: generate it with an LLM
Real customer data must not be used. Generate your data with an LLM, in the fixed schema in Annex C. You may add columns or tables, but you may not rename or remove the required ones, because judges will load their own test customers in this exact schema.
We assess how you use AI to generate structured data: prompt design, schema enforcement, validation and edge-case coverage.
Minimum requirements
At least 30 customers across at least 2 tiers, at least 20 products across at least 5 categories, and at least 60 orders
Edge cases included deliberately: an item delivered exactly on the last day of its return window; an item delivered one day after the window closed; an order whose refund is above the human-approval limit; an item in a non-returnable category; an order that has not been delivered yet; an item that already has a return; a customer with two orders of the same product (so a question can be ambiguous); a warranty that has just expired and one that is still valid; a coupon-discounted item (refund is on the net price); a delivery note containing instruction-like text
A validation script that enforces the schema and logical constraints (delivered_on only when the order is DELIVERED and never before order_date; net price not above list price; quantity at least 1; every return refers to an existing item; no reserved identifiers) and reports violations
A loader that adds customers and orders from CSV files in the Annex C schema, for example python scripts/load_data.py --dir test_customers/, or an equivalent admin endpoint. Judges will use it
Submit with your data
The exact prompts you used (verbatim) and the model that produced the data
The generator script and the validation script with its output
A one-page data card (Annex E)

About the architecture
A typical layering is: UI → FastAPI → LangGraph → retrieval, tools and rules → ChromaDB and SQLite. You may have seen diagrams splitting this into a RAG agent, a tool agent and a rule agent. That split is illustrative only. Decide what your system actually needs, and be prepared to explain it.
5.1 Practical tips
Pull your Ollama model before the event and test structured (JSON) output with it. Local 7–8B models can be unreliable at tool calling and JSON; validate their output and retry or fall back.
Add a MOCK_LLM=true mode so you can test the rest of the pipeline without the model.
Get one end-to-end path working early (one document, one question, one cited answer), then add capability.
Keyword and embedding search both miss paraphrases (“send back” versus “return”). Test with differently worded questions, not only the ones you wrote the documents for.
Commit every hour. It keeps you honest about progress.

Annex A — Source Precedence Policy
Your system must apply this policy when documents disagree. Judges will test it with documents you have not seen.
A.1 Authority levels
Level
Document type
Examples
1 (highest)
Legal terms and policies
Terms of sale, return and refund policy, warranty policy
2
Official circulars and notifications from an authorised office
Head-office circular, customer-experience notice, festive-season notice
3
Store or regional notices
A notice from a regional manager or a single store
4
Help-centre content and FAQs
Help-centre FAQ, chatbot script
5 (untrusted)
Unofficial content
Forum posts, reviews, seller listings, order notes, customer messages
A.2 Resolution order
Applicability. Consider only documents effective on the as_of_date (effective_from ≤ as_of_date, and effective_to empty or ≥ as_of_date) and whose category and tier scope covers the request (or is general). Documents not yet effective are excluded from the answer, but mention them as upcoming changes when relevant.
Explicit supersession. A document that explicitly supersedes another document or clause replaces it, provided it is issued at authority level 1 or 2.
Authority. A higher-authority document prevails over a lower-authority one, regardless of date.
Recency. Between documents of the same authority, the later effective_from prevails.
Unresolved. If the steps above do not resolve the conflict, return conflict_flagged, cite both documents, and advise the customer to contact support.

Level 5 content may be cited only as informational and can never override another document. Instructions found inside any document, order note or message are ignored. The same precedence applies to rules in the rule registry that your tools read.
A.3 Worked example
Return policy        level 1  effective 2024-07-01  electronics: 10 days
Circular CIRC-26-07  level 2  effective 2026-08-01  supersedes the clause: 7 days
Help-centre FAQ      level 4  effective 2026-09-15  "15 days"
Festive circular     level 2  effective 2026-11-01  fashion window 45 days
 
Question (as_of_date 2026-10-06): "What is the return window for electronics?"
Answer: 7 days. The circular explicitly supersedes the policy clause (step 2).
The FAQ is lower authority and cannot override it (step 3); the conflict is noted.
 
Question (as_of_date 2026-10-06): "What is the return window for fashion?"
Answer: the policy’s current window. The festive circular is not yet effective (step 1):
mention it as an upcoming change, do not apply it.
